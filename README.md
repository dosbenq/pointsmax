## PointsMax

PointsMax tells you which airline programs your points can reach for a trip
(US and India). Enter your wallet and a route: it shows, for each airline
program, the exact transfer ratio, any verified bonus running today, transfer
time, the miles that would arrive, and a link to that airline's own award
search. It shows facts only: no estimated award prices or cents-per-point.

Built with Next.js on Vercel, Postgres on Neon (Drizzle) and Better Auth for
Google sign-in.

## What Is Live

- `/us`, `/in`: the search (wallet + trip -> reachable airline programs)
- `/us/profile`: Wallet (saved balances, needs Google sign-in)
- shared trip links, privacy and terms
- Pro checkout is paused (`PRO_CHECKOUT_ENABLED`); seat availability is not
  checked yet

## Catalog Workflow

Reference data (programs, cards, earning rates, point values, transfer
partners, redemption options, booking links, hotel award charts and comparison
pages) lives as JSON in `src/data/catalog/` and ships with the build, so public
pages and the calculator keep working even if the database is down.

To change a value, edit the JSON and open a PR. `src/lib/catalog/catalog.test.ts`
checks that IDs are unique, every reference resolves, and point values use the
right unit (India in paise, everything else in US cents). Never change an
existing `id`: saved balances and affiliate clicks point at them.

Transfer bonuses are time-bound, so they stay in the database
(`transfer_bonuses`). Only rows with `is_verified = true` count; the bonus
monitor inserts detected bonuses unverified and emails `ADMIN_EMAIL`.

## Database (Neon)

User data and sign-in live in Postgres on Neon, with Better Auth for Google
sign-in. Routes that read or write user data answer 503 when the database is
unavailable (`src/lib/db/ready.ts`) rather than look like an empty account.
Profiles created before the move to Neon (November 2026) are linked by email on
their owner's first Google sign-in.

- Schema: `src/lib/db/schema.ts` holds user data and sign-in tables only. To
  change it, edit the file and run `npm run db:generate`. Commit the new SQL in
  `db/migrations` and the regenerated `src/lib/db/migrations.generated.ts`.
- Migrations are applied by the app itself on first use (`src/lib/db/migrate.ts`),
  so a deploy needs no separate step.
- `DATABASE_URL` (or `POSTGRES_URL`) selects the database. Sign-in needs
  `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `BETTER_AUTH_SECRET`. Google's
  redirect URI is `<app origin>/api/auth/callback/google`.
- `GET /api/setup/status` reports which settings are present, whether Google
  accepts the sign-in credentials and whether the schema is applied.
- Never edit a migration that has shipped (`npm run quality:migrations` checks).
- Transfer bonuses: the monitor inserts detected bonuses with
  `is_verified = false`; set it to `true` (Neon console → SQL editor) to publish one.
- Tests use an in-memory Postgres with the real migrations (`src/test/utils/test-db.ts`).
